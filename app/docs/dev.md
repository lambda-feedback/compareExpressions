# CompareExpressions
This function utilises the [`SymPy`](https://docs.sympy.org/latest/index.html) to provide a maths-aware evaluation of a learner's response.

## Architecture overview
The execution of the evaluation function follows this pattern:

- Determine context
- Parse response and answer data
- Parse criteria
- Store input parameters, parsed responses in a key-value store that allows adding new fields, but not editing existing fields
- Execute generation feedback procedure provided by the context to generate written feedback and tags
- Serialise generated feedback and tags in a suitably formatted dictionary

## Evaluation function

The main evaluation function is found in `evaluation.py` as has the following signature:

`evaluation_function(response : str, answer : str, params: dict, include_test_data=False : bool) -> dict`

### Input

This is the function that should be called to evaluate a response expression. 
- `response` is the response expression submitted by the learner
- `answer` is a reference expression provided by the task author
- `params` is a dictionary with optional parameters, for available parameters and their intended use, see the user documentation
- `include_test_data` is a boolean that controls whether some extra data useful for testing or debugging is returned

### Output

The function returns result dictionary with the following fields:
- `is_correct` is a boolean value that indicates whether the response is considered correct or not
- `feedback` is a string that provides information about what the evaluation function found when evaluating the response that is intended to be shown to the learner
- `tags` is a list of strings that encode some information about what the evaluation function has found out about the response, more consistent across similar tasks than the string output in feedback

The returned dictionary will be referred to as the `result` in this documentation.

### Overview
The overall flow of the evaluation procedure can be described as follows:

1. The function uses the parameters given in `params` to determine the context of the evaluation. What context means will be discussed in more detail in section TODO: Add section name here.
2. After the context is determined the response, answer and criteria (either supplied via `params` or from the context) are analysed an necessary information is stored for future use in a frozen `EvaluationParameters` dataclass, defined in `evaluation_parameters.py`.
3. The feedback generating procedure supplied by the context is used to generate feedback based on the contents of the `EvaluationParameters`.
4. If all criteria are found to be satisfied the response is considered correct, i.e. the `is_correct` field in the result is set to true and the feedback string and list of tags generated by the feedback generation procedure are added to their respective fields.

### Context

The context is a frozen `Context` dataclass, defined in `context/base.py`, with the following fields:
- `default_parameters` A read-only mapping where the keys are parameter names and the values are the default values that the evaluation function will use unless another value is provided together with the response. The required fields are context-dependent, currently all contexts start from the default parameters found in `context/defaults.py` and the `physical_quantity` context adds a few extra fields, see the default parameters defined in `context/physical_quantity/__init__.py`.
- `expression_parse` function that parses expressions (i.e. the `response` and `answer` inputs) into the form used by the feedback generation procedure.
- `expression_preprocess` function that performs string manipulations that makes ensures that correctly written input expressions follows the conventions expected by `expression_parse`.
- `expression_preview` is a function that generates a string that can be turned into a human-readable representation of how the evaluation function interpreted the response.
- `feedback_procedure_generator` function that generates a function for each criteria that can be used to evaluate if the criteria is satisfied or not. The output from this function should be a list of tags that the feedback string generator can use to produce human readable feedback.
- `generate_criteria_parser` function that generates a parser that can be used to turn the criteria (given in string form) into a form that the feedback generation procedure can use to determine if they are correct or not. Both contexts use parsers from `lambdafeedback.criteria`: `build_criteria_parser` (symbolic) and `build_quantity_criteria_parser` (physical quantity). The criteria string is split into individual criteria with `lambdafeedback.criteria.split_criteria` before parsing.
- `default_criteria` the criteria used when none are given in `params`.
- `parsing_parameters_generator` function that builds the parsing parameters passed to `expression_parse` from the evaluation parameters.

`select_context` in `evaluation.py` picks the context from `params`.

There are currently two different contexts:
- `symbolic`: Handles comparisons of various symbolic expressions. Defined in the `context/symbolic/` package.
- `physical_quantity`: Handles comparisons of expressions involving units. Defined in the `context/physical_quantity/` package.

Each context package exposes its `context` (a `Context`) from its `__init__.py`.

**Remark:** Handwritten expressions are sent as latex, which requires extra preprocessing before the right context can be determined in some cases. It should be considered whether a new context, perhaps called `handwritten`, should be created for this purpose.

#### `symbolic` - Comparison of symbolic expressions

**Remark:** The `symbolic` context should probably be split into several smaller contexts, the following subdivision is suggested:
- `numerical`: Comparison of expressions that can be evaluated to numerical values (e.g. expressions that are already numerical values or expressions only containing constants). Focuses on identifying if numerical values are greater than, less than, proportional to the expected answer or similar.
- `symbolic`: Comparison of symbolic expressions that cannot be reduced to numerical values.
- `equality`: Comparison of mathematical equalities (with the extra complexities that come with equivalence of equalities compared to equality of expressions).
- `inequality`: Same as `equality` except for mathematical inequalities (which will require different choices when it comes to what can be considered equivalence). It might be appropriate to combine `equality` and `inequality` into one context (called `statements` or similar).
- `collection`: Comparison of collections (e.g. sets, lists or intervals of the number line). Likely to consist mostly of code for handling comparison of individual elements using the other contexts, and configuring what counts as equivalence between different collections.

Criteria 

The criteria commands uses the following productions
```
    START -> BOOL
    BOOL -> EQUAL
    BOOL -> ORDER
    BOOL -> EQUAL
    BOOL -> EQUAL
    BOOL -> RESERVED written as OTHER
    BOOL -> RESERVED written as RESERVED
    BOOL -> RESERVED contains OTHER
    BOOL -> RESERVED contains RESERVED
    EQUAL_LIST -> EQUAL;EQUAL
    EQUAL_LIST -> EQUAL_LIST;EQUAL
    EQUAL -> OTHER = OTHER
    EQUAL -> RESERVED = OTHER
    EQUAL -> OTHER = RESERVED
    EQUAL -> RESERVED = RESERVED
    EQUAL -> OTHER ORDER OTHER
    EQUAL -> RESERVED ORDER OTHER
    EQUAL -> OTHER ORDER RESERVED
    EQUAL -> RESERVED ORDER RESERVED
    OTHER -> RESERVED OTHER
    OTHER -> OTHER RESERVED
    OTHER -> OTHER OTHER
```
along the the following base tokens:

- `START`: Formal token used to indicate the start of an expression (in practice: any expression that can be reduced to a single `START` is a parseable criterion).
- `END`: Formal token that indicates the end of a tokenized string.
- `NULL`: Formal token that denotes a token without meaning, should not appear when an expression is tokenized.
- `BOOL`: Expression that can be reduced to either `True` or `False`.
- `EQUAL`: Token that denotes symbolic equality between the mathematical expressions.
- `EQUALITY`: Token that denotes the equality operator `=`.
- `EQUAL_LIST`: Token that denotes a list of equalities.
- `RESERVED`: Token that denotes a formal name for a reserved name for an expression. Reserved names include `response` and `answer`.
- `ORDER`: Token that denotes an order operator. Order operators include `>`, `<`, `>=` and `<=`.
- `WHERE`: Token that denotes the separation of a criteria and a list of equalities that describe substitutions that should be done before the criteria is checked.
- `WRITTEN_AS`: Token that denotes that syntactical comparison should be done.
- `CONTAINS`: Token that denotes that a mathematical expression is dependent on a symbol or subexpression.
- `SEPARATOR`: Token that denotes which symbol is used to separate a the list of equalities used by `WHERE`.
- `OTHER`: Token that denotes any substring that will be passed on for more context specific parsing (e.g. explicit mathematical expressions for symbolic comparisons).

- `START`: Formal token used to indicate the start of an expression (in practice: any expression that can be reduced to a single `START` is a parseable criterion).
- `END`: Formal token that indicates the end of a tokenized string.
- `NULL`: Formal token that denotes a token without meaning, should not appear when an expression is tokenized.

- `<=`: Token for operator that checks if a quantity's value is less than or equal to another quantity's value (after both quantities are rewritten on the same units)
- `>=`: Token for operator that checks if a quantity's value is greater than or equal to another quantity's value (after both quantities are rewritten on the same units)
- `<`: Token for operator that checks if a quantity's value is less than another quantity's value (after both quantities are rewritten on the same units)
- `>`: Token for operator that checks if a quantity's value is greater than another quantity's value (after both quantities are rewritten on the same units)

##### Significant figures and decimal places

The `significant_figures`/`sig_figs`, `significant_figures_tolerance`/`sig_figs_tol`, `decimal_places`/`dp` and `decimal_places_tolerance`/`dp_tol` parameters (see the user docs) are read in `_build_parameters` (`app/evaluation.py`): `_apply_precision_aliases` copies the long names to the short ones and `_apply_precision_parameters` checks them. At most one of the four, or of `atol`/`rtol`, can be given: a conflict, or a count below the minimum (1 for `sig_figs`/`sig_figs_tol`, 0 for `dp`/`dp_tol`), raises a `ValueError`, and a count that isn't an `int` (a `bool` isn't one) raises a `TypeError`.

The tolerance forms need no code in the contexts: `sig_figs_tol` sets `rtol` to `relative_tolerance_from_sig_figs(n)` (`5*10**(-n)`) and `dp_tol` sets `atol` to `absolute_tolerance_from_decimal_places(n)` (`0.5*10**(-n)`), both in `app/context/tolerance.py`, before the parsing parameters are made, so the usual `atol`/`rtol` handling applies. Unlike `compute_relative_tolerance_from_significant_decimals` there is no `DEFAULT_SIGNIFICANT_FIGURES` floor.

`sig_figs` and `dp` are passed on as `EvaluationParameters.sig_figs`/`dp`. They check the precision the response is *written* to, so they need the response as a string: a parsed float loses trailing zeros (`92`, `92.0` and `92.00` are equal once parsed). `matches_written_precision` (`app/context/symbolic/numerical.py`) evaluates both sides numerically and calls `sig_figs_match` or `decimal_places_match`, which read the string with `read_written_number` from `expression_parsing`, compare the values rounded with `round_to_significant_figures`/`round_to_decimal_places` (within `math.ulp` of the rounded answer) and compare the written precision. `sig_figs_match` doesn't check the precision of a zero response, since the significant figures of zero aren't well defined; `decimal_places_match` does (`0` has 0 decimal places and `0.00` has 2).

Both contexts only use them for a criterion that compares `response` and `answer` directly, and there they replace the comparison rather than being a fallback, since a response equal to the answer but written to the wrong precision is incorrect:
- `symbolic`: at the top of `check_equality` (`app/context/symbolic/comparison.py`), with the preprocessed response string from `reserved_expressions_strings`.
- `physical_quantity`: in place of the value comparison in `_quantity_match` (`app/context/physical_quantity/graphs/match.py`), with the value as written in the response and the SI standard values; the units are compared as usual. `_tolerances` skips the tolerance taken from the answer's significant figures when either is set.

## Feedback and tag generation

- Generate feedback procedures from criteria, each procedure return a boolean that indicates whether the corresponding criterion is satisfied or not, a string intended to be shown to the student, and a list of tags indicating what was found when checking the criteria
- For each criterion; run the corresponding procedure and store the result, the feedback string and the list of tags
- If all criteria are found to be true, then the response is considered correct

### Tag conventions
The feedback procedures consists of a series of function calls, the specifics are determined by the particular criteria, that each return a list of strings (called tags). Each tag then indicates what further function calls must be performed to continue the evaluation, as well as what feedback string (if any) should be generated. When there are no remaining function calls the feedback procedure is completed. The tags are formatted according as *criteria*`_`*name of function call outcome*. For tags that are not connected to a specific criteria (e.g. tags that indicate an issue with expression parsing) the criteria name and underscore is omitted.

## Returning final results
The function returns result dictionary with the following fields:
- `is_correct` is a boolean value that is set to `True` is all criteria are satisfied
- `feedback` is a string that is created by joining all strings generated by the feedback procedures with a line break between each string.
- `tags` is a list of strings that is generated by joining all lists of tags generated by feedback procedures and removing duplicates.

# Preview function

When the evaluation function preview is called the code in `preview/__init__.py` will be executed. Since different contexts interpret responses in different ways they also have their own preview functions. The context-specific preview functions are `preview/symbolic.py` (symbolic expressions) and `preview/physical_quantity.py` (physical quantities), with the shared `Preview` and `Result` types in `preview/common.py`, built on the parsing from the `lambdafeedback-expression-parsing` and `lambdafeedback-units` packages, see [Packages](#packages).

**Remark**: Since it is likely that there will be significant overlap between the response preview and the response evaluation (e.g. code for parsing and interpreting the response), it is good practice if they can share as much code as possible to ensure consistency. For this reason it might be better to move the preview functions fully inside the context (e.g. by moving the preview implementation into the context packages `context/symbolic/` and `context/physical_quantity/`). In this case `preview/__init__.py` and `evaluation.py` could also share the same code for determining the right context to use.

When `is_latex` is enabled, `e` and `E` are read as plain symbols by the LaTeX parser (latex2sympy2_extended); Euler's number comes from `elementary_functions` when the result is parsed, as for text input. See the PR for the earlier latex2sympy2 workaround: https://github.com/lambda-feedback/compareExpressions/pull/235

# Packages

The parsing, unit-handling and criteria code lives in four packages from [lambda-feedback-packages](https://github.com/lambda-feedback/lambda-feedback-packages), installed through `requirements.txt` at the `v0.3.0-rc.3` release candidate. Each package's `CHANGELOG.md` lists the API changes:

| Package | Import | Used for |
|---|---|---|
| `lambdafeedback-slr-parsing` | `lambdafeedback.slr_parsing` | The SLR parser behind the criteria and quantity grammars |
| `lambdafeedback-criteria` | `lambdafeedback.criteria` | Parsing criteria, criteria graphs, turning reached criteria into feedback |
| `lambdafeedback-expression-parsing` | `lambdafeedback.expression_parsing` | Preprocessing and parsing expressions with SymPy and LaTeX |
| `lambdafeedback-units` | `lambdafeedback.units` | Unit data, reading physical quantities, dimensional analysis |

The packages don't contain feedback text. They raise typed exceptions (e.g. `BracketNotationError`) or return plain facts (e.g. `PhysicalQuantity.reverted_units`); the app maps these to a `FeedbackTag` (`feedback/tags.py`), and `feedback/symbolic.py` and `feedback/physical_quantity.py` turn them into text. The "written as" forms (`feedback/syntactical_forms.py`) live in the app for the same reason. `result.py` holds the `EvaluationResult` that collects feedback and serialises the response.

To work on the app and the packages together, install the packages from a local checkout in editable mode instead of from git:

```bash
pip install -e ../lambda-feedback-packages/slr_parsing -e ../lambda-feedback-packages/criteria \
            -e ../lambda-feedback-packages/expression_parsing -e ../lambda-feedback-packages/units
grep -v lambdafeedback app/requirements.txt | pip install -r /dev/stdin
```

# Tests
The tests are in `tests/` and fall into two main groups: evaluation tests (`evaluation_test.py` and `*_evaluation_test.py`) and preview tests (`*_preview_test.py`). Run them all with `pytest` from the repository root. The base image ships its own tests in the same `tests/` directory (e.g. `commands_test.py`, `parse_test.py`), so don't reuse those file names.

The deployed function's `healthcheck` command loads `unittest` classes from `evaluation_tests.py` and `preview_tests.py`; `evaluation_tests.py` runs the same pytest suite inside the image, so new tests only need to be written for pytest. Tests marked `@pytest.mark.slow` are left out of the healthcheck to keep it within the request timeout; mark any test function whose cases take more than about 0.5s in total.

# Imports
Modules import each other with absolute imports rooted at the `app` package (e.g. `from app.types import Parameters`), including the tests; relative imports are not used. This works both locally (run `pytest` and `mypy` from the repository root) and in the deployed image, which sets `PYTHONPATH=/app` and imports the function as `app.handler`.

# Type checking
All code in `app/` except the tests is type annotated and checked with mypy, using the configuration in `mypy.ini`. Run `mypy` from the repository root; the tools used for testing, linting and type checking (including the pinned mypy version) are listed in `requirements-dev.txt`, which CI also installs. Shared type aliases, such as `Parameters` and `GraphTemplate`, are in `types.py`. Each `# type: ignore` comment says why it is there; most mark a place where an honest type exposes a known bug.
